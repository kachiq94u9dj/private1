# CS出勤シフトアプリ 開発計画

## 1. 背景・目的

現在、CSチームの出勤シフトは Google スプレッドシート「CS出勤シフトスケジュール2026」で手作業運用されている。
- メンバーが土日の出勤可否(✕/△/●)を手入力
- シフト担当が目視で1が入った表を作成・確定
- 振替休日(代休)を手動で記録・消化管理
- 確定シフトを各メンバーの Google カレンダーに手動登録

これをアプリ化し、入力・確定・変更申請・通知・カレンダー反映までを半自動化する。

## 2. 要件サマリ(ヒアリング結果)

| 項目 | 決定事項 |
|---|---|
| 利用者・役割 | 2階層: メンバー / シフト担当(管理者) |
| データ保存先 | 既存の Google スプレッドシートを継続利用(バックエンドDBとして) |
| 実行環境 | Cloudflare (Pages + Workers) |
| 認証 | Google アカウントログイン(schoolwith.me ドメイン) |
| 通知 | Slack |
| リポジトリ配置 | `private1` リポジトリ内 `shift-app/` フォルダに同居(既存の Claude 使用量トラッカーとは独立) |

### v1 スコープ
1. 出勤可否の入力(✕/△/●)
2. シフト確定・カレンダー表示
3. 振替休日(代休)の管理
4. Google カレンダー連携(確定シフトを自動反映)
5. シフト変更・交換の申請 → シフト担当への承認確認(Slack通知)

### v1.x 追加スコープ
6. 祝日マスタ管理(シフト担当が編集可能)
7. Slack通知(申請・承認・確定などのイベント通知)

## 3. アーキテクチャ

```
┌─────────────────┐      ┌──────────────────────┐      ┌────────────────────────┐
│ フロントエンド    │─API─▶│ Cloudflare Worker(API) │─────▶│ Google Sheets API v4    │
│ Cloudflare Pages │◀────│ Hono + KV(session/cache)│     │ (専用シートをDBとして利用) │
│ React + Vite     │      │                        │─────▶│ Google Calendar API     │
└─────────────────┘      │                        │─────▶│ Slack Incoming Webhook  │
        ▲                └──────────────────────┘      └────────────────────────┘
        │ Google OAuth (schoolwith.me限定)
        └─ ログイン
```

- **フロントエンド**: Cloudflare Pages にデプロイする React(Vite) SPA。
- **API**: Cloudflare Worker(Hono)。フロントとGoogle各種APIの間に立ち、認可・バリデーション・Slack通知を担う。
- **データストア**: 既存スプレッドシートに新規タブを追加し、構造化データとして読み書きする(既存の人間可読タブはそのまま残し、履歴参照用として維持)。
- **認証**: Google OAuth 2.0。`hd=schoolwith.me` でドメイン制限。セッションは署名付きCookie + Workers KV。
- **Sheets APIアクセス**: サービスアカウント(JWT, WebCrypto で署名)を発行し、対象スプレッドシートをサービスアカウントに共有する。
- **カレンダー連携**: シフト確定時に、対象メンバーの Google カレンダー(「ルール」シート記載のメールアドレス)へサービスアカウント経由でイベントを作成/更新。カレンダー側で対象メンバーがサービスアカウントに「予定の変更権限」を共有している必要がある。

## 4. データモデル(スプレッドシート新規タブ)

既存シート「CS出勤シフトスケジュール2026」に以下のタブを追加する。

### `Members`
| id | name | email | role(counselor/supporter/manager...) | status(active/inactive) | is_admin |

### `Availability`
| id | member_id | date | symbol(✕/△/●) | note | updated_at |

### `Shifts`
| id | date | member_id | type(work/daikyu) | status(draft/confirmed) | updated_by | updated_at |

### `Requests`(変更・交換申請)
| id | type(change/swap) | requester_id | target_shift_id | proposed_date | reason | status(pending/approved/rejected) | approver_id | created_at | updated_at |

### `Holidays`
| date | name |

既存の「ルール」「Holidays」「2022年03月以降」等のタブは移行元データ・履歴参照として残し、`Members`/`Holidays`(新)への初期データ移行は Phase 0 で1回実施する。

## 5. 画面一覧

1. **ログイン画面**: Google ログインボタンのみ
2. **出勤可否入力**(メンバー): 月カレンダーで日付ごとに ✕/△/● を選択、備考入力
3. **シフト確定カレンダー**(全員閲覧、シフト担当は編集): 入力済み可否を一覧しつつ、シフト担当が確定シフトを組んで確定ボタンを押す
4. **シフト変更・交換申請**(メンバー): 対象日・希望内容・理由を入力して申請 → 承認待ち一覧に反映、Slackで管理者に通知
5. **承認待ち一覧**(シフト担当): 申請を承認/却下、コメント可能
6. **振替休日管理**: メンバーごとの代休発生・消化状況一覧
7. **祝日マスタ管理**(シフト担当): 祝日の追加・編集・削除
8. **管理者ダッシュボード**: 未確定シフト、未承認申請、通知設定への導線

## 6. フェーズ計画

| フェーズ | 内容 | 成果物 |
|---|---|---|
| Phase 0 | シート構造設計・サービスアカウント発行・認証基盤・雛形構築 | 本ドキュメント、リポジトリ雛形(今回実施) |
| Phase 1 (MVP) | 出勤可否入力 + シフト確定カレンダー(閲覧) | ログイン〜可否入力〜確定シフト閲覧まで動作 |
| Phase 2 | シフト変更・交換申請 + 承認フロー + Slack通知 | 申請〜承認〜Slack通知が一気通貫で動作 |
| Phase 3 | 振替休日管理 + 祝日マスタ管理 | 代休消化状況の可視化、祝日編集UI |
| Phase 4 | Google カレンダー自動連携 | シフト確定時に各メンバーのカレンダーへ自動反映 |
| Phase 5 | 磨き込み(通知設定、権限細分化、レポート等) | 運用フィードバックを踏まえた改善 |

## 8. 未確定・要検討事項

- カレンダー連携をサービスアカウント代理作成にするか、各メンバー個別OAuth(Calendar書き込みスコープ)にするか → サービスアカウント方式は各メンバーがカレンダーへの編集権限をサービスアカウントに共有する運用コストがある。個別OAuthは初回ログイン時の同意が必要になる。Phase 4着手前に決定。
- シフト担当(管理者)の任命方法(Membersタブの is_admin フラグで管理、UIからの付与はv1では対象外)
- 交換申請の対象範囲(全期間 or 直近◯ヶ月のみ)
